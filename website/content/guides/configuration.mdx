Commit `.branchbase.json` at the repository root. The primary worktree's copy is the project default; individual worktrees can explicitly use their own copy.

## Commands and working directories

Commands use argument arrays rather than a shell string:

```json
{
  "argv": ["bun", "run", "dev", "--port", "{apps.web.port}"],
  "cwd": "apps/web"
}
```

`cwd` is optional and must remain inside the owning checkout. Shell syntax such as pipes or `&&` is not interpreted automatically. Put multi-step behavior in a repository script and review it before approval.

With `"stop": "process"`, Start must stay in the foreground. Use a configured Stop command for detached services. Managed detached resources also need an [instance-scoped status command](/resources/managed#detached-resources).

## Endpoints and readiness

```json
{
  "web": {
    "protocol": "http",
    "readiness": { "type": "http", "path": "/health", "timeoutSeconds": 60 }
  },
  "database": { "protocol": "tcp" }
}
```

TCP readiness is the default. HTTP readiness accepts status codes `200–399` unless configured otherwise. HTTP apps receive Friendly URLs; TCP endpoints provide host and port bindings.

Omit `port` for dynamic allocation. An explicit `port` must be between 1024 and 65535; a conflict fails instead of silently selecting another port. Assigned instance ports are retained across Stop and Restart.

### Ports from a worktree's dotenv file

Use `portFromEnv` when a repository's existing setup writes local port assignments:

```json
{
  "web": {
    "protocol": "http",
    "portFromEnv": { "file": ".env.local", "variable": "WEB_PORT" }
  }
}
```

BranchBase resolves `file` from the worktree owning the run, even when the configuration is inherited from the primary worktree. It reads the named dotenv value before allocating backing endpoints and constructing environment templates. Bind the resulting port with `{apps.web.port}` as usual; Start must use that binding rather than calculate another port.

A nonempty value must be an integer between 1024 and 65535. Invalid values and occupied ports fail instead of silently choosing another port. A missing file, absent variable, or empty value falls back to `port` when supplied, otherwise normal automatic assignment. An existing automatic assignment remains stable when the file has no port.

Stop the app group before changing a file-configured port. The next Start reserves the new value and updates the backing endpoint; its Friendly URL keeps the same identity. A live run cannot be moved to another port. This stopped-instance reassignment applies only to `portFromEnv`; editing a literal `port` retains the existing explicit-reconciliation requirement.

## Environment templates

| Token | Value |
| --- | --- |
| `{apps.web.port}` | Current group's backing port for `web`. |
| `{apps.web.host}` | Backing host. |
| `{apps.web.directUrl}` | Direct HTTP endpoint. |
| `{apps.web.url}` | Friendly URL. |
| `{appGroups.services.apps.database.port}` | Selected dependency's endpoint port. |
| `{appGroups.services.outputs.database}` | A public output from the selected resource. |
| `{instance.id}` | Stable instance identity. |
| `{instance.name}` | Instance name. |
| `{worktree.id}` | Identity of the worktree owning the run. |

Map these values to the variables your application already understands. Public outputs must not contain secrets. See [manual commands and local inputs](/resources/commands) for file-backed inputs and precedence.

## Dependencies and workers

With profiles enabled, application groups depend on all infrastructure groups by default. Set `dependsOn` to choose a subset, or `[]` for an independent app. Missing dependencies and cycles are rejected.

A foreground worker can declare `"apps": {}` with `"stop": "process"`. Its running state comes from process liveness. Separate ports do not automatically isolate worker queues; configure application-specific queue names when required.

## Trust changes

Configuration edits can change the command fingerprint. Review and approve the current configuration before running it. Resource-owner recipes have their own approval, independent of the consuming project's approval.

The JSON contracts are maintained in [branchbase.schema.json](https://github.com/FranciscoMoretti/branchbase/blob/main/schema/branchbase.schema.json) and [managed-resource.schema.json](https://github.com/FranciscoMoretti/branchbase/blob/main/schema/managed-resource.schema.json).
